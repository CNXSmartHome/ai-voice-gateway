# ADR 0002: Expo with a development build for the mobile app

- Status: accepted
- Date: 2026-08-31
- Task: VG-008

## Context

`docs/ARCHITECTURE.md` names React Native as the mobile stack and stops there.
React Native has two distinct ways of being used, and the choice shapes how
every later mobile task is built, tested, and shipped:

1. **Bare React Native CLI.** `ios/` and `android/` are directories in the
   repository, edited by hand and by CocoaPods and Gradle. Building for iOS
   requires macOS.
2. **Expo with a development build.** The native projects are generated from
   `app.json` by `expo prebuild`, native modules are configured by their own
   config plugins, and EAS builds both platforms in the cloud.

The choice is not theoretical for this project. VG-007 gave the gateway a BLE
provisioning service, and the app that talks to it needs a native module
(`@orbital-systems/react-native-esp-idf-provisioning`, which wraps the
Espressif ESPProvision SDKs). A native module rules out Expo Go, which is the
usual reason people reach for the bare CLI.

The project also has an unusual constraint. `CLAUDE.md` states the goal as
building the MVP "while minimizing human intervention", and the repository is
operated by one person with a Windows workstation. Anything that requires a
Mac in the loop is not a preference, it is a bottleneck.

## Decision

Expo SDK 57, with a **custom development build** rather than Expo Go.

`ios/` and `android/` are not committed. They are generated by `expo prebuild`
from `app.json` and are listed in `.gitignore` as build output, which is what
they are.

## Consequences

**What this buys**

- **iOS without a Mac.** EAS builds both platforms in the cloud. The
  alternative puts a hardware purchase between the project and its first iOS
  build.
- **Native configuration is reviewable.** A config plugin declares an
  Info.plist key or an Android permission in `app.json`, so adding the
  Bluetooth permissions in the second half of VG-008 is a diff someone can
  read, not a change to a generated Xcode project.
- **Native modules still work.** A development build is a real native app;
  the ESPProvision wrapper is exactly the case Expo's config plugins exist
  for. Expo Go is not usable here and is not being used.
- **The bundle is verifiable in CI.** `expo export` bundles both platforms
  with no native toolchain, so an import that typechecks but cannot resolve is
  caught on every pull request. That check is already in the quality gate and
  it earned its place immediately: it caught a missing `@expo/ui` dependency
  that typechecking did not.
- **Over-the-air JS updates** are available for VG-036 and beyond without a
  store review, which matters for a product still finding its shape.

**What it costs**

- **A dependency on Expo's release cadence.** An SDK upgrade moves React
  Native, the toolchain, and every Expo package together. That is easier than
  upgrading them individually and less flexible than doing so.
- **`expo prebuild` is the source of truth for native config.** Editing a
  generated `ios/` or `android/` directory works until the next prebuild
  erases it. Native changes belong in `app.json` or in a config plugin, and
  this is the rule most likely to be broken by someone used to the bare CLI.
- **Expo's build tooling reports as a production dependency.** `expo` sits in
  `dependencies` by Expo's own convention, so `npm audit --omit=dev` sees
  `@expo/cli`, `@expo/config-plugins`, and their tree as shipping code even
  though none of it enters the bundle. The first consequence was real: a
  `uuid@7` advisory reachable only through `xcode`, a package used by
  `expo prebuild` on macOS, failed the blocking audit. It is resolved with an
  npm `override` to a patched `uuid`, which is honest -- the vulnerable
  package is actually replaced rather than excused -- but the mismatch will
  recur, and the audit job is where it will show up.
- **Ejecting is a one-way door.** Committing the native projects to escape
  Expo is possible and not reversible in practice. Nothing in the MVP is
  expected to need it; VG-018 audio streaming is the task most likely to test
  that, since it needs native audio capture on the phone side if it ever
  moves off the gateway.

## Alternatives considered

**Bare React Native CLI.** Full control of the native projects, no Expo layer,
and the conventional choice for a hardware company. Rejected because it puts a
Mac on the critical path for every iOS build, makes each dependency upgrade a
native merge, and buys control this project has no current use for. The
control is worth having when native code is being written; here the only
native code is a published module with a config plugin.

**Expo Go.** Not viable. It cannot load the ESPProvision native module, which
is the entire point of the app.
